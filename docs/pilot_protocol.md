# بروتوكول تجربة الـ Pilot مع مستخدم HR حقيقي
## نظام أتمتة إدخال الموظفين في Odoo (المرحلة 5)

> **الهدف**: اختبار استقلالية مستخدم موارد بشرية (HR) حقيقي في تعبئة القالب، وتشغيل الفحص التجريبي، وفهم التقرير، وإصدار الموافقة **دون أي شرح شفهي مسبق**، لقياس مدى وضوح الوثائق والقوالب.

---

## 📌 القواعد الذهبية للتجربة

1. **الاختبار للوثائق والنظام، وليس للموظف**: أكّد للموظف أن التجربة تقيس مدى سهولة ووضوح الدليل والقالب، وأي تعثّر هو فرصة لتحسين النظام.
2. **المراقبة الصامتة (Silent Observation)**: لا تتدخل ولا تشرح شفهياً أثناء قيامه بالخطوات إلا إذا توقف تماماً وطلب المساعدة.
3. **عدم تشغيل الكاتب الفعلي (No Live Writing)**: تقتصر التجربة على إكمال الخطوات حتى إنتاج ملف الموافقة `approval.json`. **لا يُشغَّل `writer.py` إلا بعد مراجعة صاحب المشروع المستقلة لتقرير الفحص.**

## ⏱️ مسار التجربة (4 خطوات للمستخدم)

### الخطوة 1: تعبئة 3 إلى 5 صفوف (10-15 دقيقة)
- يفتح الموظف القالب ويملأ بيانات 3 إلى 5 موظفين حقيقيين (أو مرشحين متوقعين).
- يُطلب منه ملاحظة ورقة `Reference` وورقة `Instructions`.

### الخطوة 2: تشغيل الفحص التجريبي الآمن (Dry-Run)
- يقوم الموظف بفتح الطرفية وتشغيل:
  ```bash
  python run_dry_run.py <اسم_ملفه.xlsx>
  ```
- يلاحظ المخرج الملخص على الشاشة.

### الخطوة 3: فتح التقرير وفهم الحالات
- يفتح الموظف التقرير `output/.../dry_run_report.xlsx`.
- نسأله: ما معنى حالة كل صف ظهر لك؟ ماذا ستفعل حيال الصفوف التي ظهرت بحالة `needs_review` أو `rejected` إن وُجدت؟

### الخطوة 4: إصدار قرار الموافقة (Approval)
- يشغّل أمر الاستعراض:
  ```bash
  python make_approval.py --report output/.../dry_run_report.json --list
  ```
- يعتمد الصفوف التي يراها جاهزة:
  ```bash
  python make_approval.py --report output/.../dry_run_report.json --input <الملف.xlsx> --approved-by "اسم_الموظف" --rows ...
  ```

## 🗣️ أسئلة سريعة للمستخدم بعد انتهاء التجربة

1. ما أوضح جزء في الدليل والقالب؟
2. ما أكثر خطوة أو مصطلح شعرت أنه غير واضح أو أخذ منك وقتاً طويلاً؟
3. هل تفضل تنفيذ الأوامر عبر الطرفية الحالية، أم ترى ضرورة واجهة أزرار بصرية (موقع / تيليقرام)؟
4. هل تشعر بالثقة في أن هذا الفحص يحميك من إدخال بيانات خاطئة في Odoo؟
